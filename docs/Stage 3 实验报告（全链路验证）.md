# Stage 3 全链路验证实验报告（真实系统）

---

## 1. 实验目的

本阶段将验证层面从 Stage 2（Controller 合成事件）提升至**真实 `main.py` 全链路运行**，验证系统在摄像头真实检测、终端输入、完整帧循环下的完整调度行为。

与 Stage 1/2 的关键差异：

| 维度 | Stage 1 | Stage 2 | Stage 3 |
|------|---------|---------|---------|
| 入口 | `arbitrator.submit()` | `controller.handle_event()` | `main.py`（真实 main 循环） |
| 导航来源 | 合成 arbitrator item | 合成 Event 含 objects | 真实 YOLO 检测 |
| 用户输入 | 合成 item | 合成 Event | 终端 `[Fallback Input]` |
| 帧循环 | 无 | 50ms sleep 循环 | 真实 30fps 摄像头+推理 |

---

## 2. 实验方法

### 启动方式

```bash
python main.py
```

摄像头对准桌面（含书、水杯等 2-3 个物体），每约 15 秒触发一次用户输入（在 GUI 窗口按 `a` → 等待 `[Fallback Input]` → 输入问题 → Enter）。持续 5 分钟，结束后按 `q` 退出。

用户输入内容（循环使用）：
- `前面有什么？`
- `有没有人？`
- `能描述一下环境吗？`
- `这是什么地方？`

## 4. 关键现象分析与机制解释

### 4.1 现象一：导航存活率从 0% 提升至 60%

在 Stage 3A 中，20 个导航 SUBMIT 中有 12 个被成功播放（60%），与 Stage 2 的 0% 形成鲜明对比。

**机制解释：帧间隔的自然时间离散化**

Stage 2 的 Controller runner 以 50ms 间隔循环调用 `_drain_arbitrator()`，两次 drain 之间几乎无时间差。节流耦合（`_pop_*` 更新 `last_play_time` 后立即被 `_apply_throttle` 检查）在此节奏下必然触发。

真实 `main.py` 的 drain 间隔受摄像头帧率控制（约 30fps = 33ms 间隔），加上 YOLO 推理（每 2 帧一次 ≈ 66ms 间隔）、图像编码、GUI 渲染等开销，每次 drain 间有可测量的时间差。这些微小的时间差累积后，有时恰好满足节流窗口 1.5s，使得事件得以通过。

### 4.2 现象二：VLM 100% 播放

9 个 VLM 请求全部成功返回并播放，验证了从 Controller → VLMManager → VLMCloudAdapter → callback → arbitrator → play 的完整链路在真实环境中可用。

### 4.3 核心发现：导航事件生成是视觉输入扰动驱动的，而非离散触发

Stage 3 与 Stage 2 导航存活率的极端差异揭示了一个在之前实验中未被显式建模的关键变量：

**导航事件生成 ≠ 按固定频率触发；导航事件生成 = f(视觉输入扰动)**

真实 `main.py` 中 YOLO 每帧输出波动的检测结果——边界框位置、置信度、方向、距离——这些连续扰动持续触发 DecisionMaker 的场景更新判断，生成源源不断的导航 SUBMIT。而 Stage 2 使用两套静态 objects 做离散切换，等价于用"开/关"信号模拟"连续波动"。

这一发现将系统行为的理解从"调度策略如何决定一切"推向了 **"调度行为受上游感知噪声驱动"**——调度器的决策不仅是策略逻辑的结果，还显著依赖于感知模块输出的事件密度和分布特性。

### 4.4 真实系统与合成测试的关键差异汇总

| 维度 | Stage 1/2（合成） | Stage 3（真实 main.py） |
|------|-------------------|------------------------|
| 导航事件生成 | 离散切换，产 0~1 条 | 持续流（YOLO 输出扰动） |
| 导航存活率 | 0% | 60% |
| drain 间隔 | 固定 50ms | 帧率控制 + 推理开销 |
| 用户输入行为 | 预设计时触发 | 人工敲键盘 |

## 5. 核心结论

### 结论一：系统全链路功能正确

在真实 `main.py` 运行中，72 个 SUBMIT、37 个 PLAY，覆盖了导航事件、VLM 请求、用户直接输入三种来源。无崩溃、无 deadlock、无 PLAY_FAIL。VLM 9/9 全部播放。系统具备基本可用性。

### 结论二：调度器行为对时间离散度高度敏感

节流耦合在"连续 drain"环境中（Stage 1/2 runner）杀死所有导航事件，在"帧间隔 drain"环境中（Stage 3 真实 `main.py`）允许 60% 存活。这不是策略逻辑的改变，而是物理时间结构的变化自然缓解了 `_pop_*` + `_apply_throttle` 之间的耦合。

### 结论三：调度行为是感知-调度耦合的非线性结果

三阶段实验的整体证据表明，调度系统的行为不能被视为调度策略的独立函数。导航事件生成取决于 YOLO 检测输出的连续扰动，而 YOLO 输出的扰动特性受帧率、场景复杂度和边缘设备计算能力的联合影响。

因此，Pi 上的行为是**非线性的，非单调的**——帧率降低可能导致三种不同结果：

| 场景 | 机制 | 对导航存活率的影响 |
|------|------|-----------------|
| 帧率低→drain 间隔增大 | 节流窗口自然满足 | 可能改善 |
| 帧率低→YOLO 变化更剧烈 | 每帧检测差异更大，场景更易触发变化 | 导航事件更多 |
| 延迟高→队列积压 | 堆积加剧，throttle 更激进 | 可能恶化 |

三种效应同时存在，最终效果取决于它们在 Pi 上的平衡结果。这正是 Stage 3B 实机验证无法被 PC 模拟替代的根本原因。

---

## 6. 风险与限制

- **用户输入由人工触发**：42 个 user_direct SUBMIT 中包含多次手动输入，输入节奏和频率不具有严格可复现性。
- **`throttled_drop_env` 等丢弃事件未写入 trace**：优先级 3 的节流丢弃使用 `print` 而非 `trace.log`，导致 trace 文件中无法追踪丢弃原因。
- **非阻塞延迟不等于阻塞延迟**：Pi 上 YOLO 推理会占用 CPU、阻塞主循环，改变 drain 调用的时机和频率。PC 上的帧间隔行为无法直接外推到 Pi。
