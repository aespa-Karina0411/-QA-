Stage 3 实验操作标准（实地语音测试）
========================================

版本：1.0
适用对象：实验执行者
前置要求：已通过 Stage 1 和 Stage 2，了解系统行为特点


一、实验目的
------------

本阶段为完整的实地场景测试。启用摄像头 + 麦克风 + 语音输出，
验证系统在真实使用场景下的端到端行为。

核心验证对象：

    • 完整链路：视觉 → YOLO → 用户提问 → VLM → TTS 输出
    • WARNING 零丢失是否在真实场景下保持
    • 实际环境中的调度延迟（含语音输入/输出时间）
    • 长时间运行的稳定性

本阶段要求：

    ✔ 摄像头可用
    ✔ 麦克风可用
    ✔ 音频输出可用（扬声器 / 耳机）
    ✔ 所有硬件同时接入

关于系统的行为特点，请先阅读：

    docs/系统行为说明.txt


二、实验环境要求
----------------

必须满足：

    • 树莓派 5 或 PC（建议 Pi 上执行以验证边缘部署）
    • 摄像头（USB 或 CSI）
    • 麦克风（USB 或板载，树莓派需要确认 ALSA 配置）
    • 音频输出（HDMI / 3.5mm / USB 扬声器）
    • 已安装系统依赖（树莓派需要 portaudio19-dev / alsa-utils / libsdl2-mixer-2.0-0）
    • 模型文件已就位（yolov8n.pt / Piper TTS / Vosk ASR）
    • 已通过 Stage 1 和 Stage 2

不需要：

    • GPU
    • 网络连接（可选，用于 VLM 云端推理）

部署前的完整检查清单见：

    docs/PI_PRECHECK.txt

环境搭建步骤见：

    docs/Pi上机操作手册.txt


三、启动方式
------------

【树莓派（推荐）】

    ssh pi@树莓派IP
    cd ~/edge-visionQA

    # USB 摄像头
    python main.py

    # CSI 摄像头
    CAMERA_SRC=csi python main.py

【PC 开发环境】

    cd edge-visionQA
    python main.py

正常启动后终端应显示：

    系统已启动。按 'a' 开始语音输入，按 'q' 退出。

    以及运行模式：
    [MODE] Headless (Pi / no display)     ← Pi SSH
    [MODE] Windows (GUI enabled)          ← PC

终端持续输出 trace 日志，说明系统正在运行：

    [TRACE][SUBMIT] id=... source=decision priority=3 ...
    [TRACE][SELECT] id=...
    [TRACE][SPEAK_START] ...


四、交互方式
------------

Stage 3 使用麦克风进行语音交互。操作方式取决于是否有显示屏。

【方式 A：Pi 桌面 / PC（有 GUI 窗口）】

    1. 点击摄像头画面窗口使其获得焦点
    2. 按下并按住 'a' 键，开始说话
    3. 松开 'a' 键，语音自动识别并提交
    4. 等待系统语音回答
    退出：按 'q' 键

【方式 B：树莓派 SSH（headless 模式）】

    1. 在 SSH 终端中输入 a + Enter
    2. 如果麦克风可用 → 直接说话，系统自动录音
       如果麦克风不可用 → 出现提示：

           [Fallback Input] Say something:

           在此输入文字 + Enter 作为替代
    3. 等待系统语音回答
    退出：在终端中输入 q + Enter

【重要说明】

    • Pi 上默认使用 Vosk 本地 ASR（离线语音识别）
    • 麦克风不可用时自动降级为文字输入（与 Stage 1/2 相同）
    • 语音回答通过 Piper 本地 TTS 输出（需要有扬声器或耳机）


五、实验步骤
------------

每轮测试必须包含以下操作。全程预计耗时 5 分钟。

实验 1：标准测试（必做，至少 3 轮）

    按顺序执行：

        1. 静默 30 秒
           （不说话，观察系统是否自动播报环境描述）

        2. 问 3 个问题，每次等回答完再问下一个：
           - "室内还是室外？"
           - "前面有什么？"
           - "有没有人？"

        3. 再静默 30 秒
           （观察环境播报是否在用户对话后恢复）

        4. 问 2 个问题：
           - "他戴眼镜吗？"
           - "这是室内还是室外？"

        5. 按 q 退出

    每轮必须记录：
        • 回答延迟（大致秒数）
        • 是否出现"连续等待多个回答后一起播放"
        • 是否出现回答顺序错乱（不应该发生）

    每轮结束后重启系统（Ctrl+C → 重新 python main.py）。

实验 2：压力测试（可选，在 3 轮标准测试后）

    连续快速问 5 个问题，不等前一个答完就问下一个，
    间隔约 1 秒。

    观察并记录：
        • 系统是否卡死
        • 语音是否重叠（不应该发生）
        • 摄像头画面是否卡顿
        • 回答延迟峰值（秒数）

七、结果分析
------------

收集到的 trace 文件在 PC 上分析。

7.1 快速指标计算

    python analysis/evaluate_scheduler.py logs/stage3_xxx.jsonl

    关注以下指标并与 Stage 1/2 对比：

        avg_wait_queue     实地场景下的平均等待延迟
        max_wait_queue     峰值等待延迟（应 ≤ 15s）
        warnings_dropped   必须为 0
        vlm_play_rate      VLM 回答的播放率
        output_rate        总体输出率

7.2 三阶段对比表（实验后填写）

    | 指标          | Stage 1 (纯调度) | Stage 2 (+视觉) | Stage 3 (+语音) |
    |---------------|-----------------|----------------|----------------|
    | avg_wait_queue|                 |                |                |
    | max_wait_queue|                 |                |                |
    | warnings_drop | 0               | 0              |                |
    | 环境          | 纯 stdin        | YOLO + stdin    | 全链路真实场景 |

八、通过标准
------------

全部满足以下条件视为通过：

    [1] 程序全程无崩溃退出
    [2] 各轮 trace 文件均存在且非空
    [3] trace 中包含 SUBMIT / SELECT / PLAY 事件
    [4] 不存在"SELECT 但无 PLAY"的悬空任务
    [5] warnings_dropped = 0
    [6] 至少问了 3 个不同的问题，且有明确的语音交互记录
    [7] 终端有持续 trace 输出，没有超过 10 秒的完全空白
    [8] 语音未出现重叠播放

如何验证 [4]：

    python -c "import json; events=[json.loads(l) for l in open('logs/trace.jsonl',encoding='utf-8') if l.strip()]; select_ids={e['id'] for e in events if e.get('event')=='SELECT'}; play_ids={e['id'] for e in events if e.get('event')=='PLAY'}; fail_ids={e['id'] for e in events if e.get('event')=='PLAY_FAIL'}; missing=select_ids-play_ids-fail_ids; print(f'SELECT={len(select_ids)}, PLAY={len(play_ids)}, PLAY_FAIL={len(fail_ids)}, MISSING={len(missing)}')"


九、注意事项
------------

必须遵守：

    ❌ 不要连续按 'a' 超过 5 次（可能导致 ASR 线程堆积）
    ❌ 不要拔摄像头或麦克风（运行中）
    ❌ 不要同时跑其他程序（Pi 性能有限）
    ❌ 不要修改 config 和代码文件
    ❌ 不要在语音播报中再次按 'a'（等当前回答结束）

如果出现异常：

    ✔ 记录终端中出现的所有错误信息
    ✔ 记录报错前的操作步骤
    ✔ 按 q 正常退出，或 Ctrl+C 终止
    ✔ 将错误信息和 trace 文件提交给负责人

正常现象（无需担心）：

    ✔ 回答延迟 2~12 秒（排队调度，不是卡死）
    ✔ 多个回答连续播放（堆积释放）
    ✔ 系统"看起来慢"，但终端持续有 trace 输出
    ✔ [WARN] 模型加载提示
    ✔ Headless 模式无摄像头画面窗口
    ✔ 首帧偶尔丢帧（continue 跳过，不退出）

常见问题：

    Q: 语音识别无响应？
    A: 确认麦克风已连接且未被其他程序占用。
       树莓派上执行 arecord -d 1 test.wav 检查麦克风硬件。

    Q: 没有语音输出？
    A: 确认扬声器已连接。aplay test.wav 检查音频输出。

    Q: 问完问题后等了很久没有回答？
    A: VLM 网络请求可能超时（约 8 秒），系统会给出 fallback 回答。
       如果 DASHSCOPE_API_KEY 未设置，VLM 功能不可用。

    Q: 如何判断一个回答是 VLM 给出的还是本地生成的？
    A: 终端日志中可以看到 source 字段：
       source=vlm → VLM 回答
       source=decision → 本地预置回答


核心原则
--------

    Stage 3 是完整的端到端实地验证。它建立在 Stage 1（调度基线）
    和 Stage 2（视觉负载）的基础上，检验系统在真实硬件条件下的
    综合表现。三阶段的所有 trace 数据共同构成系统行为评估的完整证据链。
